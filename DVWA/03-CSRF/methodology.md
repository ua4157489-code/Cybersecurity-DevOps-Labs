# Methodology – DVWA CSRF

## 1. Purpose

This document describes the methodology followed to identify and analyze the **Cross-Site Request Forgery (CSRF)** vulnerability in the DVWA application.

The assessment was performed in an isolated local lab environment using DVWA at:

```text
http://localhost:8080/DVWA/
```

The objective was to understand how the application handles a sensitive password-change request and determine whether adequate CSRF protection was implemented.

---

## 2. Scope

The testing was limited to the DVWA CSRF module:

```text
/DVWA/vulnerabilities/csrf/
```

The following functionality was assessed:

```text
Change Password
```

No external systems or real user accounts were involved.

# 5. Phase 1 – Reconnaissance

The DVWA application was accessed through the local browser.

The CSRF module was located from the DVWA vulnerability menu:

```text
Vulnerabilities
    ↓
Cross Site Request Forgery (CSRF)
```

The vulnerable endpoint was identified as:

```text
http://localhost:8080/DVWA/vulnerabilities/csrf/
```

---

# 6. Phase 2 – Identify Sensitive Functionality

The CSRF page contained a password-change form.

The form included:

```text
New password
Confirm password
Change
```

Password modification was selected as the target functionality because it represents a sensitive account-management operation.

---

# 7. Phase 3 – Submit Controlled Input

A controlled test password was entered:

```text
test1234!
```

The same value was entered into the confirmation field.

The request was submitted through the DVWA interface.

No real production credentials were used.

---

# 8. Phase 4 – Capture Network Request

Firefox Developer Tools was opened and the **Network** tab was used to inspect the request generated by the password-change form.

The captured request contained:

```text
GET /DVWA/vulnerabilities/csrf/
```

with the following parameters:

```text
password_new=test1234!
password_conf=test1234!
Change=Change
```

The request returned:

```text
HTTP/1.1 200 OK
```

---

# 9. Phase 5 – Analyze Authentication Context

The request was inspected for session information.

The request contained the DVWA session cookie:

```text
PHPSESSID=<authenticated-session>
```

This demonstrated that the request was being processed in the context of an authenticated DVWA session.

---

# 10. Phase 6 – Check CSRF Protection

The request was analyzed to determine whether a CSRF token was present.

A secure request would normally contain an unpredictable token such as:

```text
csrf_token=<random-value>
```

No dedicated CSRF token was observed in the captured password-change parameters.

The application therefore relied primarily on the authenticated session when processing the request.

---

# 11. Phase 7 – Analyze Request Method

The password-change functionality used:

```text
GET
```

for a state-changing operation.

This is a security concern because GET requests are generally intended for retrieving resources rather than modifying application state.

A safer design would use:

```text
POST
```

for the password-change operation.

# 13. Phase 9 – Vulnerability Assessment

The following conditions were identified:

| Security Check           | Observation      |
| ------------------------ | ---------------- |
| Sensitive operation      | Password change  |
| Request method           | GET              |
| CSRF token               | Not observed     |
| Authentication           | Existing session |
| State-changing action    | Yes              |
| Input transmitted in URL | Yes              |

These observations indicate insufficient CSRF protection in the vulnerable DVWA configuration.

---

# 14. Phase 10 – Impact Assessment

The potential impact was evaluated based on the affected functionality.

Because the vulnerable functionality modifies an account password, successful exploitation could potentially result in:

* Unauthorized password changes
* Account lockout
* Loss of account availability
* Possible account takeover
* Unauthorized modification of account settings

The actual impact in a production environment would depend on additional application security controls.

---

# 15. Phase 11 – Remediation Planning

The recommended remediation controls were identified as:

```text
CSRF Token
     ↓
Server-Side Validation
     ↓
POST Request
     ↓
SameSite Cookie Protection
     ↓
Optional Origin Validation
     ↓
Re-authentication for Sensitive Actions
```

These controls should be implemented as defense-in-depth rather than relying on a single protection.

---

# 16. Phase 12 – Verification Plan

After remediation, the application should be retested using:

### Valid Request

```text
Valid CSRF token
        ↓
Request accepted
```

### Missing Token

```text
No CSRF token
        ↓
Request rejected
```

### Invalid Token

```text
Invalid CSRF token
        ↓
Request rejected
```

### Cross-Origin Request

```text
Unauthorized origin
        ↓
Request rejected
```

---

# 17. Security Testing Principles

The following principles were followed during the assessment:

* Testing was performed only against the local DVWA environment.
* Controlled test data was used.
* No real-world accounts were targeted.
* Evidence was captured during testing.
* Findings were documented based on observed behavior.
* Remediation was considered after vulnerability identification.

## 19. Conclusion

The methodology successfully identified and documented the CSRF weakness in the DVWA password-change functionality.

The assessment confirmed that the application processes a sensitive state-changing request through a GET request without an observed dedicated CSRF token.
