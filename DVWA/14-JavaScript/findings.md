# Findings — JavaScript Attacks Lab

## Vulnerability
**Type:** Client-Side Enforcement of Server-Side Security (Reliance on Client-Side Validation)
**Location:** `/vulnerabilities/javascript/` (POST parameters `phrase`, `token`)
**CWE:** CWE-602 — Client-Side Enforcement of Server-Side Security
**Severity:** Medium
**CVSS 3.1 (estimated):** 5.3 (AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:L/A:N) — Reflects that this specific lab has low real-world stakes (a demo "win" message), but the underlying pattern (CWE-602) can carry much higher severity in real applications where client-side-only checks gate meaningful actions (e.g., price calculations, permission checks, or rate-limiting tokens).

## Description
The application generates an anti-automation/validation `token` entirely within client-side JavaScript, computed as `MD5(ROT13(phrase))`. Because this logic executes in the browser, it is fully visible to any user via "View Source" or DevTools, and can be independently reimplemented outside the browser. The server's only validation is checking that the submitted token matches this formula — it performs no check that the token was actually generated by a real browser executing real JavaScript, nor any other server-side proof of legitimate client behavior.

## Evidence

### 1. Token generation logic (fully exposed in page source)
```javascript
function generate_token() {
    var phrase = document.getElementById("phrase").value;
    document.getElementById("token").value = md5(rot13(phrase));
}
```

### 2. Independently computed token (Python, no browser involved)
```
ROT13(success): fhpprff
MD5(ROT13(success)): 38581812b435834ebf84ebcc2c6424d6
```

### 3. Cross-validated against the page's own live JavaScript
Browser console execution of the page's actual `md5(rot13("success"))` returned the identical value, confirming correctness.

### 4. Successful bypass via curl (no JavaScript execution at all)
```bash
curl ... -d "phrase=success&token=38581812b435834ebf84ebcc2c6424d6&send=Submit"
```
**Server response:** `"Well done"`

## Impact
- **In this specific lab:** minimal — the only consequence of bypassing is a "Well done" success message, with no sensitive data or state change involved.
- **General pattern risk (why this matters beyond this lab):** CWE-602 as a category can be severe when the pattern is applied to real security decisions — e.g., a client-side "is this user an admin" check controlling UI visibility but not enforced server-side, a client-side price calculation trusted at checkout without server recomputation, or (closer to this lab's exact mechanism) a client-side anti-bot token that a real application relies on to rate-limit or gate an expensive server operation. In all such cases, the same technique demonstrated here — reading the client logic and reimplementing it outside the browser — defeats the control entirely.
- **Automation/bot-bypass risk:** If this pattern were used as an actual anti-automation measure (e.g., preventing scripted mass-submission of a form), this lab demonstrates it provides no real protection — any scripted client can compute valid tokens without ever loading a browser or executing JavaScript, defeating the presumed purpose.

## Root Cause
Security-relevant logic (token generation intended to prove "a real browser executed this") is implemented entirely in client-side JavaScript with no server-side equivalent verification. The server trusts a value that was computed by code it has no control over and cannot verify was actually executed as intended, rather than the server generating and validating security tokens itself.
