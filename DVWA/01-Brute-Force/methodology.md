# DVWA Brute Force — Testing Methodology

## 1. Assessment Overview

This assessment was conducted to evaluate the resistance of the DVWA Brute Force module against repeated password-guessing attempts.

The assessment followed a structured workflow:

```text
Scope Definition
      ↓
Application Discovery
      ↓
Request Analysis
      ↓
Manual Testing
      ↓
Automated Testing
      ↓
Response Analysis
      ↓
Evidence Collection
      ↓
Risk Assessment
      ↓
Remediation Recommendations
      ↓
Validation
```

The target was a deliberately vulnerable DVWA instance running locally.

---

# 2. Scope

### Target

```text
http://localhost:8080/DVWA/
```

### Vulnerable Functionality

```text
/DVWA/vulnerabilities/brute/
```

### Test Account

```text
admin
```

### Security Level

```text
Low
```

### Authorization

Testing was performed against a local intentionally vulnerable application in an isolated lab environment.

---

# 3. Phase 1 — Application Discovery

The DVWA application was accessed through the local web server.

The available vulnerability modules were reviewed to identify the Brute Force functionality.

The relevant endpoint was identified as:

```text
/DVWA/vulnerabilities/brute/
```

### Objective

Determine:

* Target application
* Relevant functionality
* Authentication interface
* Attack surface
* Required parameters

---

# 4. Phase 2 — Request Analysis

The browser Developer Tools Network panel was used to inspect the HTTP request generated by the login form.

The request structure was identified as:

```text
GET /DVWA/vulnerabilities/brute/?username=admin&password=<PASSWORD>&Login=Login
```

### Identified Parameters

| Parameter  | Purpose               |
| ---------- | --------------------- |
| `username` | Target username       |
| `password` | Password candidate    |
| `Login`    | Login form submission |

The request also contained a session cookie:

```text
PHPSESSID=<SESSION_ID>
```

and the DVWA security-level cookie:

```text
security=low
```

### Objective

Understand exactly how authentication requests are constructed before performing automated testing.

---

# 5. Phase 3 — Manual Validation

Before automation, individual password candidates were tested manually.

Example:

```bash
curl -i \
  -H 'Cookie: PHPSESSID=YOUR_SESSION_ID; security=low' \
  "http://localhost:8080/DVWA/vulnerabilities/brute/?username=admin&password=admin123&Login=Login"
```

The application returned:

```text
Username and/or password incorrect.
```

This established the baseline response for a failed authentication attempt.

---

# 6. Phase 4 — Successful Authentication Validation

A valid credential was tested manually.

Example:

```bash
curl -i \
  -H 'Cookie: PHPSESSID=YOUR_SESSION_ID; security=low' \
  "http://localhost:8080/DVWA/vulnerabilities/brute/?username=admin&password=password&Login=Login"
```

The response contained:

```text
Welcome to the password protected area admin
```

This established the response pattern associated with successful authentication.

---

# 7. Phase 5 — Response Differentiation

The successful and unsuccessful responses were compared.

### Failed Authentication

```text
Username and/or password incorrect.
```

### Successful Authentication

```text
Welcome to the password protected area admin
```

Both responses returned:

```text
HTTP/1.1 200 OK
```

Therefore, HTTP status code alone was not sufficient to identify successful authentication.

The response body was used as the validation indicator.

---

# 8. Phase 6 — Automation

After manual validation, a Bash script was used to automate password-candidate testing against the local DVWA endpoint.

The automation performed the following logical workflow:

```text
Read password candidate
        ↓
Submit authentication request
        ↓
Receive HTTP response
        ↓
Inspect response
        ↓
Successful response?
      ↙     ↘
    No       Yes
    ↓         ↓
Next         Stop
candidate    testing
```

The resulting output was:

```text
[-] Failed: 123456
[+] Password found: password
```

---

# 9. Phase 7 — Vulnerability Confirmation

The vulnerability was considered confirmed when the following conditions were satisfied:

* The authentication endpoint was identified.
* Repeated password attempts were accepted.
* The application returned distinguishable authentication responses.
* Automated password testing was possible.
* A valid credential was identified in the intentionally vulnerable lab.

### Final Result

```text
Vulnerability: Brute Force Authentication
Status: Confirmed
```

# 11. Phase 9 — Risk Assessment

The finding was evaluated based on:

### Exploitability

The authentication endpoint was straightforward to identify and automate in the lab.

### Authentication Controls

Effective brute-force protections were not present at the selected DVWA security level.

### Credential Strength

A weak password was accepted by the intentionally vulnerable application.

### Potential Impact

If similar weaknesses existed in a real application, an attacker could potentially compromise user accounts.

---

# 12. Phase 10 — Remediation Analysis

The following controls were recommended:

### Authentication Protection

* Rate limiting
* Progressive delays
* Account protection
* MFA

### Password Security

* Strong password policy
* Block commonly used passwords
* Secure password hashing

### Application Security

* Use POST for credential submission
* Enforce HTTPS
* Avoid exposing credentials in URLs

### Security Monitoring

* Log authentication failures
* Monitor repeated login attempts
* Detect successful logins after multiple failures
* Generate SIEM alerts for suspicious patterns

---

# 13. Phase 11 — SOC Detection Perspective

The same attack can be detected through authentication logs.

Example:

```text
10:15:01  admin  Login Failed
10:15:02  admin  Login Failed
10:15:03  admin  Login Failed
10:15:04  admin  Login Failed
10:15:05  admin  Login Failed
10:15:06  admin  Login Success
```

This pattern should be investigated because a successful login immediately following numerous failures may indicate credential compromise.

### Investigation Workflow

```text
Alert
  ↓
Identify source IP
  ↓
Identify targeted account
  ↓
Count failed attempts
  ↓
Check successful authentication
  ↓
Review post-login activity
  ↓
Determine legitimacy
  ↓
Contain if malicious
  ↓
Document incident
```

---

# 14. Phase 12 — Validation Plan

After remediation is applied, the same authorized test should be repeated.

The expected result is that excessive authentication attempts are:

```text
Blocked
   OR
Rate Limited
   OR
Delayed
   OR
Require Additional Verification
```

The validation should also confirm that:

* Authentication failures are logged.
* Security alerts are generated.
* MFA is enforced where applicable.
* Legitimate users can still authenticate.
* Credentials are not exposed in URLs.
* Repeated attempts cannot continue unrestricted.

---

# 15. Methodology Summary

The assessment followed a repeatable security-testing process:

```text
1. Define Scope
2. Identify Attack Surface
3. Analyze HTTP Request
4. Establish Failed-Login Baseline
5. Establish Successful-Login Baseline
6. Automate Testing
7. Analyze Responses
8. Confirm Vulnerability
9. Collect Evidence
10. Assess Risk
11. Recommend Remediation
12. Define Validation Tests
```

This methodology can be reused for other authentication-security assessments.

---

# ⚖️ Ethical Considerations

This assessment was performed only against a deliberately vulnerable DVWA instance hosted locally for educational purposes.

Brute-force testing against production systems, third-party applications, or accounts without explicit authorization is prohibited and can cause account lockouts, service disruption, or unauthorized access.

The objective of this lab was to develop practical skills in:

* Web application security
* Authentication testing
* HTTP analysis
* Security assessment methodology
* Vulnerability documentation
* SOC detection and incident investigation
